# Findings

Contradictions and gaps found in the brief, the portal and the starter repo. The brief says "a contradiction is a finding", so each one is recorded here rather than silently resolved. Every item was checked against its source on **2026-09-30** (1–11) and **2026-10-01** (12). Where a choice had to be made, the decision is stated.

| # | Finding | Sources that disagree | Decision |
|---|---|---|---|
| 1 | **Can you resubmit?** | Portal *Rules* §7 and *FAQ*: "You may resubmit multiple times before the deadline; only your latest valid submission will be judged." Repo `README.md`, `RULES.md` R8, the portal *Submit* page and the Google Form: submission is final, no resubmission. | Treat submission as **final and one-shot** (the stricter reading, and the one on the form itself). |
| 2 | **Where does the submission go in the fork?** | `GITHUB-GUIDE.md`: no participant folder is needed. `submissions/_TEMPLATE/README.md`, `.github/pull_request_template.md` and the `submission-guard` workflow all assume `submissions/<username>/`. | Everything lives in `submissions/Bhargav200/`. The fork's root README links to it. |
| 3 | **Required fork name isn't a valid GitHub name.** | Portal *My Track*: "paste the generated name exactly: `cube26-rcv-0263-https://github.com/bhargav200`". GitHub doesn't allow `:` or `/`, and turned it into `cube26-rcv-0263-https-github.com-bhargav200`. The portal's Verify field placeholder repeats the URL twice. The FAQ says not to rename the fork. | Kept GitHub's sanitised name, unchanged. |
| 4 | **How many scoring criteria?** | Portal *Rules* §3 and §8: "7 criteria". Repo `README.md`: 5 criteria (15 / 25 / 25 / 20 / 15 = 100). The organisers' main site (sydon.ai/cube) lists "7 pillars of CUBE engineering" (agent engineering, problem solving, system integration, modern workflow, reliability, production thinking, technical ownership), which is probably what the portal's "7 criteria" refers to. | Built against the repo's 5-criterion table, the only one with point weights, and kept the 7 pillars in view (e.g. fail-open and timeouts for reliability, the decision rationale in every record for technical ownership). |
| 5 | **Is a deployment required?** | Portal *Submit* page: "Deployment URL, if applicable". Google Form: Deployment URL is a required field. | Deployed, using a hosted vision model (see README). |
| 6 | **The eval set.** | `data/README.md`: "Your eval set is separate: 50 units your agent has never seen, labelled independently by two humans." Repo `README.md`: "Your fixtures and eval set are yours to capture." No eval set or photos ship with the repo. | Captured our own held-out photo set; the size and number of labellers are stated in the eval report. |
| 7 | **Referenced documents are missing.** | Repo `README.md` promises a domain brief (economics, fee structures, a warehouse day), "the official evidence contract provided by the organisers", and a worked Returns Manager package. The Google Form points to an "Official Participant Handbook". None of these is in the repo, on the portal, or linked from the form. | Wrote our own evidence contract (`contract/`, v0.2), mirroring the sample CSV's vocabulary. No economic figures are quoted, because there was no authoritative source to look them up in (engineering rule 5). |
| 8 | **Individual build, cross-pod score.** | Round 2 is individual, and Rules forbid collaborating. The repo `README.md` says "Your output has to be usable by another pod … and it's scored". The template lists a contract "as agreed with the other pods". | The contract is published and versioned, but not agreed with anyone; it says so. |
| 9 | **Same ASIN for two products.** | `data/receiving_sample.csv`: `B0DUMMY357` is both `SKU-PROT-1KG` (Whey Protein) and `SKU-LAMP-LED` (LED Desk Lamp). | Identity matches on the product title and SKU, never on ASIN alone. |
| 10 | **Is a wrong colour/variant an identity failure?** | In the sample CSV every row flagged `wrong_colour` or `wrong_variant` also has `identity_match = no`. The brief lists identity and "wrong colour, wrong variant" as separate things. | Kept **separate** checks (`identity` = right product, `variant_colour` = right version), so one never hides the other. |
| 11 | **Portal example vs "UNCERTAIN is valid".** | The portal's worked example marks Variant PASS on "Blue" alone. The same page says "Do not invent evidence. Only match what is explicitly documented or visible." When the variant is a size (e.g. 750 ml) that isn't legible, colour alone doesn't prove it. | The colour is checked separately. A size/variant not printed on the label is UNCERTAIN. The portal example reproduces exactly (quantity FAIL, variant PASS, damage FAIL, EXCEPTION) when the label shows the variant: test "the portal's worked example" in `agent/tests/decide.test.ts`. |
| 12 | **Merged, or pushed?** | Main site (sydon.ai/cube): Round 2 is judged on "working code merged into the starter repo" ("Merged, or it did not happen"). `GITHUB-GUIDE.md` §5: "No pull request is required": work stays in your own fork. | Final code is on the fork's `main` branch, which is what the guide describes and what evaluators see by default. |

Finding 3 affects the fork-verification step on the portal. The fork URL is `https://github.com/Bhargav200/cube26-rcv-0263-https-github.com-bhargav200`.

These can also be raised as GitHub Issues labelled `finding` on the fork, as the repo README asks.

## Use of AI coding tools

The organisers' main site FAQ says AI coding tools (ChatGPT, Claude, Gemini, Copilot, Cursor or equivalents) are permitted, and that the participant is responsible for understanding, testing, validating, explaining and defending what they submit. AI coding assistants were used in this build. Every design decision and its rationale is written down in [ARCHITECTURE.md](ARCHITECTURE.md) and [build-log.md](build-log.md), and the behaviour is covered by the test suite and the eval.
